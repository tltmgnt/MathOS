# Phase VIII — recursive separator messages

Run from repository root: `python tools/mra_x_separator.py --output separator-evidence.json`. Local environment Python 3.13.5, NumPy 2.3.5, SciPy 1.17.0. The extension uses separators of size one or two in the induced primal graph of the current private region, favoring balance within the first successful size. Leaves are at most four variables when splitting succeeds, but unsplittable regions can be larger. Separator size is not a bound on induced width, because ancestor boundaries can accumulate. Input admission is 128 variables, domain sizes up to four, and 1024 factors; the predicted full enumeration count must fit the specified budget. This is not a wall-time or memory limit.

## Semantics and reuse
For a private region, route every factor that touches a child to that child. No original factor can touch distinct children because those private regions lie in different components after separator removal. A child's projection onto remaining variables cannot create an edge between sibling private regions. The returned factors summarize the minimum over its eliminated variables, with local backpointers retained. Process children first and then the separator. Terminal constant factors give the optimum, and reversing the global trace gives an attaining assignment when feasible. This is an informal induction argument; the actual certificate check replays all local minima independently of the recursive cache.

With fixed domains, scopes and hierarchy, a node's input factor tables determine its output messages and trace. Cache keys compare complete ordered factor contents, including missing rows and duplicate factors. A node hit reuses its projection and witness records; a miss recomputes its own separator after recursively considering children. Retain descendants on parent hits for later partial edits. Scope edits require a new engine; there is no incremental topology restructuring.

## Results
12 connected problems across chains, cycles and overlapping ternary factors, sizes 8,16,32,64; all initial optima agreed with actual SciPy/HiGHS and the flat reference. Three eight-variable cases also checked by exhaustive enumeration. 60 table updates (empty factor, restore, empty constant, restore, unchanged), all matched fresh fixed-order optimum, witness and trace; both flat cache comparison paths matched objective values. Six boundary/budget/scope controls passed. The two full reports were byte-identical. Maximum hierarchy depth five; separator sizes up to two, induced width up to three. 120 subtree hits.

Initial hierarchical enumeration: 5,472 vs min-fill 3,462 (+58.06%). Updates excluding setup: 1,502 vs fresh hierarchical recomputation 27,360 (-94.51%); flat bucket reuse on same hierarchical order 1,394 (hierarchy 7.75% worse); flat min-fill bucket reuse 4,864 (hierarchy 69.12% lower). Including initial setup, hierarchy 6,974 vs flat min-fill reuse 8,326 (-16.24%). These are logical evaluation counts, not wall time or memory; cache-key creation, copies, verification and planning are excluded. The strong gain is relative to the chosen order and edit pattern; hierarchical caching did not beat same-order bucket caching. No automatic policy promotion, globally optimal order certificate or original RE-X integration. Lean proof, independent replication, larger benchmarks and true structural edit reuse remain open.
