# Phase XXII — compositional SMT certificates

Run python3 tools/mra_x_compose.py --output compose-evidence.json with Python 3.11+ and libz3 (tested Z3 4.13.3.0). An opt-in checker accepts original factors, claimed result, and all projected messages from an untrusted solver. It independently partitions the active factors by elimination variable, derives each separator, verifies projected table/trace schema and enumerated cost counters, and checks each local certificate. For every claimed row, directly evaluate its specified witness to establish attainment. One quantifier-free SMT query per fresh bucket excludes any feasible original row missing from the projection, any cost below the claimed minimum, or an earlier minimizing value. This checks completeness, dominance and deterministic tie-breaking. Then insert the checked projection, continue through the permutation, verify terminal constants and reconstruct the witness in reverse, evaluating its original cost. No reference elimination or solver cache metadata is trusted for this chain. The input validation and SMT encoder are shared with prior modules.

Mathematical composition argument: by induction over the elimination order, each validated local projection preserves feasibility and attained global optimum under the untouched factors (Phase XXI relational obligations). Every feasible terminal result can be lifted through the stored witnesses in reverse order, because each separator consists exclusively of later variables. The verifier also checks the final original witness directly. Three additional simple symbolic checks establish rank transitivity, lower-bound composition and local cost equality for witness lifting. These are mathematical steps, not a mechanized induction theorem or a refinement proof of Python.

A trusted in-process receipt is reused only when the eliminated variable, all involved domain sizes, full input factor multiset, projected scope/table and witness rows match exactly. Hashes are not used as a substitute for equality. The checker scans all buckets and stages receipt replacement until the complete certificate succeeds; a failed verification leaves old receipts intact. This is a result-level verification boundary: it can detect wrong cached projections or witnesses but does not prove that the solver's dirty queue, termination, runtime, actual-work counters, database or physical machine are correct. The receipts are trusted mutable process memory, not exported solver proof objects, not authenticated durable artifacts.

## Executed evidence

Each campaign: 22 generated networks from 11 families, five states each (initial, identical repeat, reordered domain expansion, forbidden unary insertion and removal), two states of a 128-variable chain, three boundary cases. 115 full solution certificates, 48 feasible and 67 infeasible. 1,007 bucket obligations: 370 fresh local SMT queries and 637 exact receipt hits (63.26% fewer local solver invocations than checking every bucket anew); 1,594 row attainment checks on fresh buckets. 47 small states additionally checked by whole-instance SMT (71 queries). All accepted. Three symbolic arithmetic obligations UNSAT. Nine deliberately corrupted certificates rejected: wrong cost, missing row, nonminimal attained row, wrong tie break, wrong scope, wrong final witness, wrong full count, wrong order, Boolean witness entry. Failed checks preserve receipts; a valid repeat still reuses both receipts in the control case.

Across 22 unchanged repeats, all 150 receipts reused, zero local SMT calls. Domain migrations reuse 105/150 receipts. Forbidden unary insertion and removal each reuse 128/150. The 128-variable chain initial certificate requires 128 queries; its local edit requires two, reusing 126. Both complete reports byte-identical, report digest checked; same local environment, not independent replication. Query counts do not include symbolic checks, whole-instance checks or negative controls. No runtime or memory benchmark. Lean, proof-object export and independent verification, general program refinement, actual original RE-X integration and remote CI confirmation remain open. Default solver unchanged.
