# Phase XXIV — compressed proof intelligence and incremental trusted verification

Run python3 tools/mra_x_archive_audit.py --directory archive-audit (new directory). Check a single archive with python3 -I -S tools/mra_x_archive.py FILE --expect-archive EXPECTED_SHA256. The checker imports only the Python standard library. The optional expected archive hash must be supplied from a separately trusted source; it binds the exact canonical representation, not provenance or mathematical equivalence.

The archive stores unique objects (factor tables and pairs of projected messages and witness records) with SHA-256 digests. Ordered state manifests reference these objects by integer indices, preserving factor multiplicity, domains, result fields and problem fingerprints. The verifier checks every object hash and reference, rejects unused and duplicate objects, and reconstructs each state from original factors and verified projections. It checks local completeness, lower bounds, attainment and deterministic witness selection as in Phase XXIII. Reuse requires exact immutable equality of the eliminated variable, all local domain sizes, full input factor multiset, projected table and witness rows; the first state is verified from scratch and receipts retain only the previous accepted state's keys. On each fresh process replay, all trust is reconstructed locally; no saved receipt, object hash or manifest is trusted as proof. All states are scanned and the entire archive is rejected on a failed state. This is a standalone result checker, not a proof-assistant-certified kernel.

Limits: 8 MB file, 128 states, 32768 unique objects, 128 variables per state, 1024 original factors, domains 1–4, cost/claimed optimum magnitude <=10^100, full local enumeration <=1,000,000 per state and <=8,000,000 per archive, actual factor lookups <=5,000,000 per state. Direct Python API calls do not enforce the byte limit. Limits do not guarantee absolute runtime/memory or adversarial security. No authenticated storage, OS sandbox, random-access trusted restoration or hard memory cap.

## Matched local evidence

12 new synthetic streams (chain, cycle, overlapping ternary factors; 8,32,64,128 variables), eight states each: initial, value change, restore, no-op, forbidden unary insertion/removal, domain expansion/reordered migration, no-op. Each campaign: all 96 states (84 feasible, 12 infeasible) accepted by both Phase XXIII full checker and Phase XXIV archive checker; all 12 archives rechecked in fresh isolated Python processes. 5568 bucket obligations, 4137 exact receipt hits. Full visits 55478 vs fresh archive visits 12978 (-76.61%); factor lookups 116609 vs 30461 (-73.88%). Raw canonical JSON arrays 1293522 bytes vs archives 476579 (-63.16%). 12076 references to 1891 unique objects across the separate archives. Gzip on the same arrays and archives gives 122543 vs 126229 bytes (+3.01% archive regression): deduplication is not a claim of superior general-purpose compression.

Twenty rejection controls per campaign, including corrupted hashes, wrong expected fingerprint, bad references, duplicate/unused objects, rehashed wrong mathematical claims, changed factor multiplicity, state and byte limits, duplicate JSON keys and deliberately reduced visit/lookup limits. Two local reports reproduce all non-timing evidence and verify their evidence digests.

Five randomized-order timing repeats per policy per stream (120 total timed executions per campaign), measured from resident canonical JSON bytes including decoding, hashing and checking, excluding disk I/O, generation and process startup. Geometric mean of per-stream median archive/full ratios 0.735229 and 0.733210; worst ratios 0.881446 and 0.895666. All streams improved on these local measurements. Separate single tracemalloc measurement per stream/policy: geometric mean peak traced allocation ratio 0.342190 in both campaigns, worst 0.475723. This is Python traced allocation, not RSS or maximum process memory; baseline loads a complete eight-document array rather than streaming individual certificates, so memory comparison depends on loading strategy. No independent replication, external benchmark, or deployed policy change. Candidate for review, not automatic promotion.

The next step is a bounded streaming archive reader with independently anchored manifests and an explicit comparison against streamed and compressed baselines. Lean certification, original RE-X physical-logical correspondence, implementation refinement and remote CI confirmation remain open.
