# Phase XXXVI — persistent computational state and copy-on-write staging

Run python3 tools/mra_x_fork_audit.py --directory fork-audit (new directory). The opt-in Store uses the Phase XXXIV verified compressed-checkpoint pipeline unchanged except for private speculative execution staging. Phase XVII execute normally deep-copies the whole indexed engine for ordinary edits, but Phase XII Indexed.update already copies outer containers and affected route dictionaries, and replaces edited factor tables, messages and records rather than mutating their previous contents. Phase XXXVI makes a shallow engine fork before that existing update. Domain/order migrations use the original executor. The same independent routed certificate gate reconstructs the committed engine and receipts, and publication occurs after SQLite commit. Deep is a matched profiling control using the same new pipeline with the original deep-copy stage. No changes to previous default solver or storage policies.

The private fork shares mutable Python objects by convention; it is not an immutable state API, a security boundary or literally zero-copy. It assumes trusted existing Indexed.update, preparation, checker, sequential access, and no in-place mutation of shared objects by arbitrary code or concurrent callers. The helper must not expose its speculative engine outside trusted code. The public Store.apply result contains scalar receipt/profiling fields, not internal tables. Snapshot materialization, full structural validation, trace copying, encoding and persistence still occur. Reopen reconstructs trust from persisted checked mathematics; no saved receipt is trusted. No new authentication, power-loss coverage, arbitrary fault containment, formal program proof or original physical RE-X integration.

Two complete local campaigns on six new-seed synthetic streams (16/64 variables; chain, cycle, overlapping ternary factors; value edits at beginning/middle/end of factor list, restore, no-ops, forbidden factor and recovery, domain expansion/contraction). Each has 16 edits, for 96 transaction states (90 feasible, six infeasible), 288 matched method-results per campaign across Phase XXXIV, Deep and Store. Every state checked against fresh reference, standalone certificate fingerprint and historical retrieval; old engine snapshots checked unchanged, retained history checked, one reopen per method per stream. Per campaign 84 shallow forks and 12 original migration executions, all methods 9181 solver visits, 37965 full verification visits, 8804 fresh visits, 2926 receipt hits, 417792 allocated SQLite page bytes. Eleven controls per campaign: shared no-op object identity, isolated returned trace, witness-only update, budget rollback, injected objective/trace/input-ID errors, SQL insert abort, stale writer, caller table mutation isolation, migration and reopen. These are selected controls, not arbitrary in-place corruption of shared state. Both reports reproduce identical non-timing evidence and their digests verified.
